0.1 원문 요구사항과 설계 보완의 구분

이 문서는 다음 두 종류의 내용을 구분한다.

[원문 필수]
첨부 원문에 직접 명시된 요구사항이다. 임의로 축소하거나 다른 기능으로 대체하지 않는다.

[구현 결정]
원문 요구사항을 실제로 안정적으로 구현하기 위해 추가한 기술적 결정이다. 원문에 없는 요구사항을 원문인 것처럼 취급하지 않는다.

0.2 원문에서 반드시 유지할 핵심 의도

- 통계분석 전문가가 웹서비스를 쉽게 제작하는 플랫폼이어야 한다.
- 비개발자도 Page, Layout, Element, Database 연결을 최대한 쉽게 구성할 수 있어야 한다.
- UI의 기준은 shadcn/ui이며, 아이콘은 Lucide를 사용한다.
- 기본 제작 순서는 Page/Layout 설계 → DB 및 Element 연결 → 실제 데이터 입출력 검증이다.
- Page는 더블클릭 이름 변경, Drag & Drop 순서 변경, 빨간 휴지통 아이콘 삭제를 지원한다.
- Drag 중에는 매달려 흔들리는 듯한 “대롱거리는” 시각 효과를 제공한다.
- Layout은 Preset과 Element Palette를 제공하고, Grid에 맞춰 자동 정렬하며, 8방향 Resize를 지원한다.
- 선택한 Element의 상세 속성은 우측 패널에서 설정한다.
- DB 구성 화면은 Class Diagram 형태이며 Page, Element, DB를 Node로 표현한다.
- Node와 연결선은 마우스로 조작하며 Auto Layout을 제공한다.
- 최종 서비스는 로컬 PC에서 실행되고 webeditor.dove9999.com으로 접근한다.

0.3 원문 표현 “shadcn/ui의 모든 구성 요소 사용”에 대한 구현 규칙

원문의 의도를 문자 그대로 보존하기 위해 다음과 같이 구현한다.

- shadcn/ui를 제품의 유일한 기본 UI Component Source로 사용한다.
- 초기 Repository 구성 시 shadcn CLI의 전체 Component 설치 결과를 Dry Run으로 검토한 후 Stable Component를 모두 설치한다.
- `/internal/design-system` 경로에 설치된 모든 shadcn Component의 동작과 Theme를 확인하는 Component Gallery를 만든다.
- 실제 제품 화면에는 의미에 맞는 Component만 사용한다. 단순히 “사용 횟수”를 채우기 위해 부적절한 UI를 억지로 배치하지 않는다.
- shadcn Component를 직접 수정할 때는 공통 Design Token과 접근성을 깨뜨리지 않는다.
- 외부 UI Kit를 혼합하지 않는다. 기능상 필요한 전용 Library는 Canvas, Graph, Chart Engine처럼 shadcn이 제공하지 않는 영역에 한해 사용한다.

0.4 Lucide 사용 규칙

- 일반 UI Icon은 모두 `lucide-react`를 사용한다.
- Emoji, Font Awesome, Material Icons, Heroicons 등 다른 Icon Pack을 섞지 않는다.
- 사용자는 Element 속성에서 Lucide 전체 Icon Catalog를 검색·선택할 수 있어야 한다.
- 실제 Bundle에는 사용한 Icon만 포함되도록 Tree Shaking 또는 동적 Import를 적용한다.
- 삭제 Icon은 `Trash2`, 설정은 `Settings`, DB는 `Database`, Page는 `FileText`, 연결은 `Link2`, 해제는 `Unlink`, 검증 성공은 `CircleCheck`, 경고는 `TriangleAlert`, 실패는 `CircleX`로 통일한다.


0.5 추가 요구사항 통합 원칙

2026-08-15 대화에서 접수된 추가 요구사항은 다음과 같이 해석하고 본 문서 전체에 통합한다.

A. 완성된 운영 웹페이지의 Page Navigation은 왼쪽에 둔다.
- 편집 화면의 Page Manager도 왼쪽에 유지한다.
- Published Runtime은 왼쪽 Sidebar를 기본 Navigation Shell로 사용한다.
- Page별 Lucide Icon, Page Name, 현재 Page 상태를 동일하게 표시한다.

B. Data Relationship Canvas의 연결 방향은 Port 위치와 선의 방향으로 동시에 표현한다.
- 모든 입력(Target) Port는 Node 왼쪽에 둔다.
- 모든 출력(Source) Port는 Node 오른쪽에 둔다.
- Edge는 오른쪽 Source에서 시작하여 왼쪽 Target으로 끝난다.
- Arrowhead, Edge Label, 선택 상태, 흐름 표시를 함께 사용하여 방향을 색상만으로 구분하지 않는다.

C. Page Icon은 Page의 영구 속성이다.
- Editor에서 Page Icon 클릭 시 Lucide Icon Selector를 연다.
- 선택한 Icon은 Metadata, Draft Preview, Published Runtime, 왼쪽 Navigation에 동일하게 반영한다.

D. Theme는 Editor와 Runtime이 동일한 Semantic Token Contract를 사용한다.
- Editor에서 Project Default Theme 또는 Custom Theme를 변경하면 Draft Preview에는 즉시 반영한다.
- `autoApplyThemeToRuntime=true`인 경우 Contrast Validation을 통과한 Theme Revision만 Published Runtime Theme Channel에 자동 적용한다.
- Page/Element/Data Definition의 Immutable Published Version과 Theme Revision을 분리하여 자동 Theme 반영과 안전한 Rollback을 동시에 만족한다.
- Runtime 사용자는 허용된 60개 Preset 또는 Project에서 공개한 Theme 중 하나를 선택할 수 있다.
- Runtime 사용자의 Theme 선택은 Project별·Browser Profile별로 저장한다.

E. Node Edge는 Orthogonal Routing을 기본으로 한다.
- 수평·수직 직선 구간을 최대한 길게 유지한다.
- 방향 전환 구간에만 작은 Corner Radius를 적용한다.
- 과도한 Bezier Curve는 사용하지 않는다.
- Node를 피하고 불필요한 꺾임을 최소화한다.

F. Element를 Page에 놓기 전 실제 배치 위치와 크기를 보여준다.
- Grid Snap 후의 예상 x, y, w, h를 반투명 Placeholder로 표시한다.
- Drop 결과는 Preview와 정확히 일치해야 한다.

G. 60개 Theme는 Web Research를 바탕으로 설계한다.
- Nord, Solarized, Catppuccin, Dracula, GitHub Primer, IBM Carbon, Material 3, Radix Colors, Gruvbox, Tokyo Night, Rosé Pine, Everforest, Ayu, One Dark/Light, Night Owl, Kanagawa 등 공개된 Theme/Design System을 조사한다.
- 원본을 무비판적으로 복제하지 않고 WebEditor의 Semantic Token과 WCAG 기준에 맞게 재해석한다.
- 사용자 화면에 원본 상표명을 그대로 노출할지는 License/Trademark Review 후 결정한다.
- 내부 Metadata에는 `referenceFamily`와 `adaptationNote`를 남긴다.

H. 구현 완료 후 표본 검사가 아니라 Inventory 기반 전수 검증을 수행한다.
- 구현된 모든 Page Type, Layout Preset, Element Type, Property, Action, Binding, Field Type, Theme, Font Size, Resize Handle, Browser State를 검증 목록에 등록한다.
- 등록된 항목 중 미검증 항목이 1개라도 있으면 Release Gate를 통과하지 못한다.

I. 기능 전수 검증 후 약 100개의 실제 Project를 생성하여 운용 검증한다.
- 빈 이름만 다른 Project가 아니라 규모, Page, Element, DB, Binding, Theme, Navigation이 서로 다른 실제 Project를 생성한다.
- 100개 모두에서 저장, 재접속, Runtime, Data I/O, Theme, Navigation, Soft Delete/Restore를 실제 수행한다.
- Project 간 데이터 격리를 Sentinel Data로 검증한다.

J. Project 삭제는 Recycle Bin 기반 Soft Delete로 구현한다.
- 일반 Project 목록의 Delete Button은 물리 삭제를 하지 않는다.
- Project Metadata와 Project Storage를 휴지통 상태/영역으로 이동한다.
- Recycle Bin에서 복구할 수 있다.
- Permanent Delete는 Recycle Bin에서만 별도 강한 확인 절차를 거쳐 수행한다.
- Delete/Restore/Purge 전 과정은 Audit Log와 검증 대상이다.

0.6 원문과 추가 요구사항이 만나는 지점의 결정

- 원문의 Page 우측 빨간 Trash2는 Page 삭제 기능으로 유지한다.
- 추가 요구사항의 Project 삭제 버튼은 Project Home의 Project 단위 Trash2이며 Page 삭제와 별개다.
- Page 삭제는 Editor Undo가 가능한 Command 기반 삭제로 처리한다.
- Project 삭제는 Recycle Bin으로 이동하는 Soft Delete로 처리한다.
- Editor Draft와 Published Runtime을 분리한다는 기존 안전 원칙은 유지한다.
- 단, Theme는 별도 Versioned Theme Channel을 통해 검증 통과 후 자동 반영할 수 있게 하여 “운영 화면 자동 적용” 요구사항을 만족한다.

1.2 핵심 가치

사용자가 코드를 직접 작성하지 않고도 다음 작업을 수행할 수 있어야 한다.

1) Project를 생성하고 Project Home에서 관리한다.
2) Page를 생성하고 Page별 Lucide Icon과 왼쪽 Navigation 순서를 정한다.
3) Layout Preset을 선택하거나 빈 Canvas에 Element를 배치한다.
4) Element를 Drop하기 전에 실제 배치 위치와 크기를 확인한다.
5) DB Table과 Field를 만든다.
6) Page/Element/DB를 왼쪽 입력 Port와 오른쪽 출력 Port를 사용하여 시각적으로 연결한다.
7) Sample Data를 실제 Test DB에 입력한다.
8) Page를 실행하여 조회, 입력, 수정, 삭제, 이동을 검증한다.
9) Editor Theme를 Runtime Theme와 동기화하고 Runtime 사용자의 Browser별 Theme 선택을 허용한다.
10) 검증된 Version을 Publish한다.
11) Project를 휴지통으로 이동하고 필요하면 복구한다.

1.5 제품 완료의 의미

다음 세 단계가 모두 끝나야 “완료”라고 부른다.

LEVEL 1 — IMPLEMENTED
- 요구사항에 대응하는 코드와 UI가 존재한다.

LEVEL 2 — EXHAUSTIVELY VERIFIED
- Feature Inventory의 모든 항목이 PASS다.
- Mock, Placeholder, TODO, Disabled Stub가 없다.

LEVEL 3 — OPERATIONALLY VERIFIED
- 서로 다른 약 100개 실제 Project가 생성되어 100/100 핵심 시나리오를 통과한다.
- 삭제/복구, 서버 재시작, Browser 재접속, Project 격리까지 통과한다.

LEVEL 1만 완료하고 프로젝트 전체를 완료로 보고하지 않는다.

2.1 요구사항 추적 방식

- 각 REQ는 `docs/requirements/REQ-xxx.md` 또는 단일 Traceability Table에 구현 파일, Test ID, Evidence Artifact를 연결한다.
- 상태 값은 `NOT STARTED`, `IN PROGRESS`, `BLOCKED`, `IMPLEMENTED`, `VERIFIED`, `EXHAUSTIVELY VERIFIED`, `OPERATIONALLY VERIFIED`, `RELEASED`만 사용한다.
- `IMPLEMENTED`는 코드가 있다는 뜻일 뿐 완료가 아니다.
- 개별 기능은 최소 `VERIFIED`, 전수 검증 대상은 `EXHAUSTIVELY VERIFIED`, 100개 Project 운용 대상은 `OPERATIONALLY VERIFIED`여야 한다.
- Release Gate는 모든 필수 REQ가 요구된 최종 상태에 도달해야 한다.
- Evidence는 Test Report, Screenshot, Video/Trace, DB Query Result, Log, Checksum 중 하나 이상을 포함한다.

└────────────────────────────────────────────────────────────────────┘

4.2 가장 중요한 분리 원칙

A. Editor와 Runtime Renderer를 분리한다.
- Editor Component를 그대로 Published Runtime에 재사용하지 않는다.
- Runtime Renderer는 Project Definition만으로 Page를 그릴 수 있어야 한다.
- Editor용 Selection Border, Resize Handle, Grid Guide는 Runtime에 포함하지 않는다.
- Editor와 Runtime은 UI Shell은 다르지만 동일한 Page Definition, Icon Name, Semantic Theme Token Contract를 사용한다.

B. Metadata DB와 Runtime DB를 분리한다.
- `webeditor.sqlite`: Project, Page, Element, Binding, Version, Theme Revision, Validation, Trash State 등 Builder 자체 데이터
- `test.sqlite`: Sample Data와 Editor Preview용 실제 데이터
- `production.sqlite`: Published Runtime용 실제 데이터

C. Draft와 Published Version을 분리한다.
- Draft는 Auto Save로 계속 변경된다.
- Published Version은 Immutable Snapshot이다.
- Production Runtime은 Published Snapshot만 읽는다.
- Theme는 별도 `ThemeRevision`으로 Versioning한다.
- `autoApplyThemeToRuntime`이 켜져 있으면 검증 통과 Theme Revision만 Published Theme Pointer를 갱신한다.
- Theme 자동 적용 실패가 Published Page/Data Version을 손상시키지 않는다.

D. Display Name과 Physical DB Identifier를 분리한다.
- Table 표시명 변경으로 실제 Table Rename을 유발하지 않는다.
- 예: 표시명 `Measurement Result`, 실제명 `t_8f31a2`
- Field 표시명 `Vth`, 실제명 `c_104ac9`
- 모든 Binding은 UUID 기반으로 유지한다.

E. Active Project와 Trashed Project를 분리한다.
- Active Project만 Editor와 Published Runtime에서 열 수 있다.
- Trashed Project는 Metadata, Runtime DB, Asset을 보존하지만 실행하지 않는다.
- Permanent Delete 전까지 Project ID를 재사용하지 않는다.
- Delete/Restore/Purge는 Project Lifecycle Transaction과 Outbox를 사용한다.

F. Visual Edge와 Executable Binding을 분리하지 않는다.
- 화면에 Edge가 존재하면 대응 Binding Record가 반드시 존재한다.
- Binding이 삭제되면 Edge도 삭제된다.
- Source/Target Port ID와 Direction은 저장 계약의 일부다.

4.4 기술 선택 이유

- Visual Editor는 Client-side 상호작용이 대부분이므로 Vite SPA가 단순하고 빠르다.
- API와 Runtime Engine을 별도 Fastify Server로 분리하면 Local Hosting과 Windows Service 구성이 단순해진다.
- React Grid Layout은 Grid Snap, 외부 Drop, 충돌, 8방향 Resize를 제공하므로 자체 Layout Engine을 새로 만드는 위험을 줄인다.
- dnd-kit DragOverlay는 Drag 대롱 효과와 Drop Preview를 원래 Layout Flow에서 분리할 수 있다.
- React Flow는 Node/Port/Edge Editor에 적합하며 ELK는 여러 고정 Port를 고려한 Auto Layout을 지원한다.
- SmoothStep 또는 Custom Orthogonal Edge는 직선 구간과 작은 Corner Radius를 구현하는 데 적합하다.
- Metadata는 정형 Schema이므로 ORM을 사용한다.
- 사용자가 만드는 Runtime Table은 동적으로 바뀌므로 정적 ORM Model에 억지로 넣지 않고 별도 Safe SQL Compiler를 사용한다.
- Project Recycle Bin은 단순 UI 상태가 아니라 Metadata/Storage/Runtime Availability를 함께 제어해야 하므로 독립 Lifecycle Service가 필요하다.

6. Canonical Project Model
======================================================================

6.1 원칙

- Project Definition은 JSON 직렬화가 가능해야 한다.
- ID는 UUID를 사용한다.
- 이름 변경으로 ID가 바뀌지 않는다.
- 모든 저장 객체에 `schemaVersion`, `revision`, `createdAt`, `updatedAt`을 둔다.
- Runtime은 Published Project Definition의 Version을 명시적으로 읽는다.
- Page Icon은 `iconName`으로 저장하고 Lucide Catalog Version과 함께 검증한다.
- Connection Direction은 `sourcePortId`, `targetPortId`, `sourceSide=right`, `targetSide=left`로 저장한다.
- Theme는 Project Definition의 선택 정보와 별도 Theme Revision을 가진다.
- Project Lifecycle 상태는 Active/Trashed/Purging/Purged를 명시한다.

6.5 Project Lifecycle State Machine

ACTIVE
→ TRASHING
→ TRASHED
→ RESTORING
→ ACTIVE

TRASHED
→ PURGING
→ PURGED

규칙:
- ACTIVE가 아닌 Project는 일반 Editor Open 및 Runtime Serve를 금지한다.
- TRASHING/RESTORING/PURGING 중에는 중복 명령을 409로 거부한다.
- 각 전환은 idempotencyKey를 지원한다.
- Metadata 변경과 File Move 사이의 실패를 Outbox Recovery로 복구한다.
- PURGED는 Tombstone과 Audit Record만 남기며 Project ID를 재사용하지 않는다.

8.3 Theme Token Contract

각 Preset은 이름만 다른 Theme가 아니라 다음 Semantic Token을 모두 가져야 한다.

background, foreground
card, card-foreground
popover, popover-foreground
primary, primary-foreground
secondary, secondary-foreground
muted, muted-foreground
accent, accent-foreground
destructive, destructive-foreground
border, input, ring
chart-1 ~ chart-8
sidebar, sidebar-foreground, sidebar-primary, sidebar-primary-foreground
sidebar-accent, sidebar-accent-foreground, sidebar-border
canvas, canvas-grid, canvas-grid-strong
selection, selection-foreground
node, node-foreground, node-border
edge, edge-selected
success, success-foreground
warning, warning-foreground
error, error-foreground
info, info-foreground

Token 저장 형식:
- Source of Truth는 JSON.
- CSS에서는 shadcn/ui Semantic CSS Variable로 변환한다.
- Chart에서도 동일 Theme Variable을 사용한다.
- Theme Revision에는 Token Checksum을 저장한다.

8.4 Theme 품질 Gate

필수 자동 기준:
- 일반 Text / Background: Contrast Ratio 4.5:1 이상
- Card Text / Card: 4.5:1 이상
- Primary Text / Primary: 4.5:1 이상
- Accent Text / Accent: 4.5:1 이상
- Muted Text / Muted: 4.5:1 이상
- Sidebar Text / Sidebar: 4.5:1 이상
- Node Text / Node: 4.5:1 이상
- Focus Ring / 인접 Background: 3:1 이상
- 필수 Input Boundary / Background: 3:1 이상
- Selection Boundary / Background: 3:1 이상
- Chart Mark / Canvas: 3:1 이상
- Status는 Icon+Label+Shape를 같이 사용하며 색상만으로 구분하지 않는다.
- Disabled Text도 제품 내부 기준 3:1 이상을 목표로 한다.
- 60개 Token Hash는 모두 달라야 한다.
- Preset 간 배경·주요색의 OKLCH/DeltaE 유사도 검사를 수행하고 사실상 중복 Theme를 금지한다.

수동 품질 기준:
- 10px~24px Font Size
- Hover, Focus, Active, Selected, Disabled
- Dialog, Popover, Table, Form, Chart, Sidebar, Canvas, Node
- 밝은 실내, 어두운 실내
- 색각 이상 Simulation
- Windows Forced Colors

8.6 Editor → Runtime Theme 동기화

Editor Token 변경
→ Draft Theme Revision 생성
→ Contrast/Schema/Visual Smoke Validation
→ PASS이면 `publishedThemeRevisionId` 갱신
→ Runtime WebSocket/SSE 또는 짧은 Poll로 Revision 감지
→ CSS Variable 무중단 교체
→ 실패 시 이전 Published Theme 유지
→ Audit Log와 Rollback Point 생성

원칙:
- Theme 변경 때문에 Page/Data Published Version을 다시 생성하도록 강제하지 않는다.
- Theme Validation이 실패하면 자동 적용하지 않는다.
- Runtime 사용자의 Browser Override가 있으면 새 Default Theme가 배포되어도 Override를 유지한다.
- 사용자가 선택한 Theme가 허용 목록에서 제거되면 새 Default로 Fallback한다.

10.4 Drop Placement Preview

Element가 Canvas 경계 안에 진입하는 순간 반투명 Placeholder를 표시한다.

Placeholder가 보여야 하는 정보:
- 예상 Left/Top 위치
- 예상 Width/Height
- Grid x, y, w, h
- Element Type과 Icon
- 배치 가능/불가능 상태
- 충돌로 인한 자동 이동 여부

표시 예:
`X: 4  Y: 12  W: 8  H: 10`

동작 규칙:
1. Pointer 위치를 Canvas Local Coordinate로 변환한다.
2. Zoom과 Scroll Offset을 보정한다.
3. Element Registry의 defaultW/defaultH를 읽는다.
4. Grid Snap을 적용한다.
5. Canvas Boundary를 적용한다.
6. Collision Resolver를 실행한다.
7. 최종 예상 x/y/w/h를 Placeholder에 그린다.
8. Drop 시 같은 계산 결과를 재사용한다.

정확성:
- Preview와 실제 Drop 결과의 x/y/w/h가 완전히 같아야 한다.
- Drop 시 별도 계산으로 결과가 달라지지 않게 `placementCandidateId` 또는 동일 Snapshot을 사용한다.
- 1 Grid라도 다르면 E2E Test 실패다.

시각 상태:
- Valid: Theme `selection` Outline + 반투명 Surface
- Collision Resolved: Warning Icon + 이동된 위치
- Invalid: Destructive Outline + 금지 Cursor
- Out of Bounds: Canvas 외부 영역은 Clip
- Reduced Motion: 흔들림 제거, Placeholder는 유지

Element별 기본 크기:
- Text/Badge/Button: 작은 Default
- Input/Form: 중간 Default
- Chart/Table/Board/Chat: 큰 Default
- Registry에서 min/max Size와 함께 정의한다.

======================================================================

15.1 Node Type

PAGE NODE
- Page Icon
- Page 이름

- Element 수

- 오른쪽 Navigation/Containment Output Port

- Element Icon

선택적으로 DATA SOURCE GROUP NODE를 제공한다.

15.2 Port 방향 규칙

절대 규칙:
- Input/Target Port는 Node 왼쪽에만 배치한다.
- Output/Source Port는 Node 오른쪽에만 배치한다.
- Edge 생성 Drag는 오른쪽 Output Port에서 시작한다.
- Drop은 왼쪽 Input Port에서 끝난다.

Port Shape:
- Input: 안쪽을 향하는 Triangle 또는 Concave Marker + 원형 Hit Area
- Output: 바깥쪽을 향하는 Triangle 또는 Convex Marker + 원형 Hit Area
- 색상만으로 Input/Output을 구분하지 않는다.
- Tooltip에 `Input`, `Output`, Value Type, 허용 Binding Type을 표시한다.

Port ID:
`<objectId>:<role>:<direction>:<index>`

예:
- `element-123:data-x:input:0`
- `table-456:field-vth:output:0`

같은 Node에 같은 Type의 Handle이 여러 개 있으면 모든 Handle에 고유 ID가 있어야 한다.

15.3 Edge Type과 Direction

- CONTAINS: Page Output → Element Input
- READ: DB Field Output → Element Data Input
- CREATE: Form/Button Output → DB Table/Field Input
- UPDATE: Form/Button Output → DB Table/Field Input
- DELETE: Button/Table Row Output → DB Table Input
- FILTER: Variable/Input Output → Binding Filter Input
- NAVIGATE: Element/Page Output → Target Page Input
- RELATION: Source Table Field Output → Target Table Field Input

Direction 시각화:
- Target 끝에 Arrowhead
- Edge 중앙 또는 시작 근처에 Binding Type Label
- 선택 Edge에는 짧은 Flow Dash 또는 이동 Dot
- Reduced Motion에서는 Animation을 제거하고 Arrowhead/Label은 유지
- Read/Write/Navigate는 색상뿐 아니라 Label과 Line Pattern으로도 구분
- 반대 방향 연결 시도는 Port Highlight를 하지 않고 금지 Cursor를 표시

15.4 Point-to-Point 연결

- Output Port Drag 시작 시 호환 가능한 왼쪽 Input Port만 강조한다.
- 호환되지 않는 Port는 Drop 불가.
- Input Port에서 Drag 시작은 기본적으로 금지한다.
- 필요 시 “Reverse Connect Gesture”를 제공할 수 있으나 결과 Edge Direction은 항상 Source Right → Target Left로 정규화한다.
- Drop 시 Binding Wizard를 연다.
- Wizard에서 Mapping, Aggregate, Filter, Sort, Write Mode를 설정한다.
- 연결 완료 전에 Preview Query와 Sample Output을 표시한다.
- Binding Wizard 취소 시 임시 Edge를 제거한다.

15.5 Orthogonal Rounded Edge

기본 경로:
- 수평/수직 Segment로 구성한다.
- Source 오른쪽에서 최소 `sourceStub=16px` 수평으로 나간다.
- Target 왼쪽으로 최소 `targetStub=16px` 수평으로 들어간다.
- 방향 전환은 90도다.
- Corner Radius 기본값은 8px, 범위는 4px~12px다.
- Bezier Curve를 기본으로 사용하지 않는다.

Routing 우선순위:
1. Bend 수 최소
2. Node 내부 통과 금지
3. Node Border와 최소 12px 거리
4. Edge Crossing 최소화
5. Edge Length 최소화
6. Label 공간 확보

기본 구현:
- React Flow `smoothstep`을 기반으로 Custom Edge를 구현하거나
- Orthogonal Router를 별도 구현한다.
- Node 회피가 필요하면 Grid 기반 A*/Jump Point 또는 ELK Edge Section을 사용한다.
- 외부 Library 추가 시 License와 Bundle Size를 ADR에 기록한다.

불필요한 꺾임:
- 같은 Y축에서 직접 연결 가능하면 한 개 수평 Segment
- 단일 중앙 Channel로 연결 가능하면 2 Bend 이하
- 일반 연결은 4 Bend 이하를 목표
- 4개를 초과하면 Router가 재탐색하고 Warning Metric을 기록

15.6 Edge 교차 시각화

- 교차 자체를 최대한 줄인다.
- 교차가 불가피할 때 선택적 Line Jump/Bridge를 사용한다.
- 선택 Edge를 위 레이어로 올린다.
- Edge Label이 다른 Edge나 Node와 겹치지 않게 Offset한다.
- 여러 Edge가 동일 Port를 사용할 경우 시작 Segment를 Fan-out한다.

15.7 Node 이동과 저장

- 모든 Node는 자유롭게 이동한다.
- Position은 Project ID + Object ID 기준으로 저장한다.
- Zoom/Pan/Viewport도 사용자별로 저장한다.
- Node 이동 중 Edge Path를 실시간 또는 Throttled Recompute한다.
- Node 이동 종료 후 최종 Route와 Position을 저장한다.
- 새로고침 후 동일 위치와 Port Direction을 복구한다.

15.8 Auto Layout

- 기본 방향: Left to Right.
- 권장 Layer: Page → Element → Database 또는 실제 Data Flow Direction.
- ELK Layered Algorithm 사용.
- Fixed Port Order와 Fixed Side를 사용한다.
- Input Port는 WEST, Output Port는 EAST로 전달한다.
- 목표:
  1) Node Overlap 0
  2) Edge Crossing 최소화
  3) Direction Layer 유지
  4) Port 순서 유지
  5) 연결되지 않은 Node 별도 정렬
  6) Fit View
- Auto Layout 결과를 Preview한 뒤 Apply/Cancel.
- Apply는 하나의 Undoable Command.
- 사용자가 수동 조정한 Node를 Pin할 수 있다.

15.9 Direction Validation

차단 대상:
- Input → Input
- Output → Output
- 왼쪽 Source → 오른쪽 Target으로 저장되는 연결
- 동일 Port의 허용 개수 초과
- Data Type 불일치
- 순환 금지 Action의 Cycle
- Trashed/Deleted Object 연결
- Hidden Invalid Page 연결

Validation Error에는 Source Node, Source Port, Target Node, Target Port와 수정 방법을 표시한다.

15.10 Edge Test Matrix

- 모든 Edge Type
- 같은 행
- Source가 Target보다 위/아래
- Source가 Target 오른쪽에 수동 배치된 비정상 위치
- Node 사이 장애물 0/1/다수
- 1개 Port에 Edge 1/10/50개
- Node Drag 중 Path Update
- Zoom 50%~200%
- Auto Layout 전/후
- Reduced Motion
- Theme 60개
- Arrowhead/Label/Pattern 가시성

18.5 Published Runtime

권장 경로:
- `/apps/<project-slug>/...`

Editor 인증과 Published App 공개 범위는 분리한다.

공개 범위:
- Private
- Authenticated
- Public

1차 Release 기본값은 Private이다.

Project가 TRASHED 상태면:
- Published Runtime API는 실행하지 않는다.
- Public Route는 Project Unavailable 또는 410 상태를 반환한다.
- Restore 후 Health/Binding Check가 PASS해야 Runtime을 다시 활성화한다.

18.6 Theme Resolution

1. Browser Preference 조회
2. 허용 Theme인지 검사
3. Published Theme Revision 조회
4. Project Default Theme 조회
5. Built-in Fallback
6. CSS Variables 적용
7. `data-theme-id`와 `data-theme-revision` 설정

Theme 변경:
- 전체 React Tree를 재생성하지 않는다.
- CSS Variable 교체로 즉시 적용한다.
- Chart는 Theme Revision Event를 받아 Color를 갱신한다.
- 사용자 입력값과 Scroll 위치를 유지한다.

18.7 Runtime Theme 자동 갱신

Editor에서 새 Theme Revision이 자동 Published됨
→ Runtime이 Revision Notification 수신
→ 현재 사용자가 Project Default를 사용하는지 확인
→ Default 사용자에게 새 Theme 적용
→ Browser Override 사용자는 기존 선택 유지
→ 선택 Theme가 삭제/금지된 경우 Default로 Fallback
→ 실패하면 이전 CSS Variable Snapshot으로 Rollback

18.8 Runtime State Persistence

Browser별 저장:
- Theme ID
- Font Size
- Sidebar Collapse
- Navigation Group Collapse

Key Namespace에 Project ID를 포함하여 다른 Project와 섞이지 않게 한다.

24. Auto Save와 Versioning
======================================================================

24.1 Auto Save

- 변경 후 500ms Debounce.
- Network 실패 시 IndexedDB Queue에 임시 저장.
- 재연결 시 Revision 확인 후 동기화.
- 저장 성공을 확인하기 전 “Saved” 표시 금지.
- Page Icon, Layout, Binding Route, Theme Draft도 Auto Save 대상이다.

24.2 Project Snapshot

- 큰 변경 또는 Validation 직전에 Draft Snapshot 생성.
- Published Version은 수정 불가.
- Version에는 Project Definition Checksum과 Validation Run ID를 포함한다.
- Project Snapshot은 Theme Revision ID를 참조하지만 Theme Token 전체를 중복 저장할지 여부는 ADR로 결정한다.

24.3 Theme Revision

Theme 수정은 별도 Revision을 만든다.

Revision 상태:
- DRAFT
- VALIDATING
- VALID
- INVALID
- PUBLISHED
- SUPERSEDED

Auto Apply:
- `autoApplyThemeToRuntime=false`: Project Publish 시 반영
- `autoApplyThemeToRuntime=true`: Theme Validation PASS 직후 Published Theme Pointer 갱신
- 실패 시 기존 Pointer 유지

24.4 Publish Gate

Publish 전 필수:
- Critical Validation Error 0
- Inventory Validation 필수 범위 PASS
- Test Runtime E2E 통과
- Production DB Backup 성공
- Schema Migration Plan 확인
- Published Definition 생성 성공
- Page Icon 존재 검사
- Runtime Left Navigation 검사
- Node Port Direction 검사
- Theme Contrast 검사

24.5 Final Release Gate

제품 전체 Release 전 필수:
- REQ-001~REQ-037 모두 VERIFIED
- Feature Inventory 미검증 0
- 60 Theme Visual/Contrast PASS
- 100-Project Verification 100/100 PASS
- Trash/Restore/Purge Recovery Drill PASS
- TODO/Placeholder/Skipped Test Scan PASS

24.6 Rollback

- Project Published Version Rollback
- Theme Revision Rollback

- 각 Rollback은 독립적으로 실행 가능해야 한다.

25. Security 명세
======================================================================

25.1 기본 보안

외부 Domain으로 노출되므로 인증 없는 Editor를 운영하지 않는다.

- Local Admin Account
- Argon2id Password Hash
- Secure, HttpOnly, SameSite Cookie
- CSRF Protection
- Login Rate Limit
- Session Expiration
- Audit Log
- Lifecycle Operation Authorization

25.2 Network

- Application은 기본적으로 `127.0.0.1`에만 Bind한다.
- Public Inbound Port를 직접 열지 않는다.
- Cloudflare Tunnel을 권장한다.
- 필요 시 Cloudflare Access를 추가한다.

25.3 SQL/Runtime

- Arbitrary SQL 금지.
- Arbitrary JavaScript 금지.
- Identifier는 Metadata Allowlist.
- Value는 Parameterized Query.
- Query Row Limit 기본 10,000.
- Query Timeout과 Cancellation.
- SQLite Runtime Limit을 보수적으로 설정.
- TRASHED/PURGING/PURGED Project의 Runtime Query는 거부한다.

25.4 File Upload

- 허용 Extension/Size 제한.
- Path는 UUID로 저장.
- 원본 파일명을 File System Path에 직접 사용하지 않는다.
- 실행 파일 업로드 금지.
- 다운로드 시 Content-Disposition과 MIME 검증.
- Trash/Restore 시 Asset Path Traversal을 검사한다.

25.5 Project Lifecycle Security

Project Trash:
- Editor 권한 필요
- CSRF 보호
- expectedRevision
- idempotencyKey
- 영향도 Dialog

Project Restore:
- Editor 권한 필요
- 이름/Slug 충돌 강제 해결
- Manifest Checksum 검증
- DB Integrity Check

Permanent Delete:
- Admin 권한
- Recycle Bin에서만 실행
- Typed Confirmation
- 최근 Re-authentication 권장
- Purge Plan과 실제 삭제 대상 Checksum 일치
- Audit Log
- 실패 시 Compensation/Recovery

25.6 Browser

- Content Security Policy
- X-Frame-Options 또는 frame-ancestors
- Referrer Policy
- X-Content-Type-Options
- Secure Headers
- Runtime Theme Preference JSON을 신뢰하지 않고 허용 Theme ID만 적용
- localStorage에 Secret이나 DB Credential을 저장하지 않는다.

25.7 Internal Verification API

- 100-Project Corpus API는 Admin/Internal Route로 제한한다.
- Public Runtime Bundle에서 노출하지 않는다.
- Test Project 이름과 Data에 실제 개인정보를 넣지 않는다.
- Verification Artifact에 Password/Token/Secret을 기록하지 않는다.

28.1 목적과 원칙

Testing은 “대표 예시 몇 개가 동작하는지”를 확인하는 절차가 아니다. 최종 단계에서는 구현된 기능, Element, Layout, Theme, 상태, 권한, 데이터 흐름, 배포 구성을 Inventory로 수집하고 누락 없이 전수 검증한다.

LEVEL A — 정적 품질 검사
LEVEL B — Unit Test
LEVEL C — Integration Test
LEVEL D — Component/Interaction Test
LEVEL E — Vertical Slice E2E

28.10 약 100개 실제 Project 운용 검증 Corpus

기능 전수 검증이 PASS한 후에만 정확히 100개의 실제 Project를 생성한다. Project 이름만 바꾼 복제본 100개는 인정하지 않는다.

Corpus 구성:

- 10개 Minimal/Blank-to-First-Page Project
- 20개 Standard Dashboard Project
- 20개 Statistical Analysis Project
- 15개 Data Entry/CRUD Project
- 15개 Multi-page Navigation/Variable Project
- 10개 Complex Node/Binding Graph Project
- 5개 Accessibility/High-Contrast Project
- 5개 Stress/Recycle-Bin/Recovery Project

합계: 100개

Corpus 설계 규칙:

- 60개 Theme가 최소 1회 이상 실제 Project Default로 사용되어야 한다.
- 모든 Page Type, Layout Preset, Element Type, Binding Type이 Corpus 전체에서 최소 1회 이상 사용되어야 한다.
- 각 Project에 고유한 `projectSentinel`과 Runtime Row Sentinel을 저장한다.
- Project별 데이터, 파일, Theme, Binding이 다른 Project에 노출되지 않아야 한다.
- 최소 10개 Project는 20 Page 이상, 최소 10개는 100 Element 이상, 최소 5개는 100 Node 이상으로 구성한다.
- 테스트용 Project라는 이유로 Frontend Mock이나 Memory DB를 사용하지 않는다.
- 일반 사용자가 사용하는 동일 API와 동일 저장 경로를 사용하되 Production Data와 분리된 Test Workspace에서 실행한다.

각 Project에서 공통으로 수행할 검증:

1. 생성
2. Page/Element/DB/Binding 구성
3. 저장
4. Browser Reload
5. Server Restart
6. Editor 재진입
7. Runtime Preview
8. Published Runtime
9. 실제 Read/Write
10. Navigation
11. Theme 변경 및 유지
12. Export/Import 또는 Backup 확인
13. Project 검색/정렬
14. Soft Delete
15. Recycle Bin 표시
16. Restore
17. 데이터·파일·Sentinel 동일성 확인

영구 삭제는 복구 검증을 끝낸 별도 복제 Fixture에서 수행한다. 영구 삭제 후 Metadata, Runtime DB, Uploaded Asset, Backup Reference, Search Index의 잔존 여부를 검사한다.

29.1 Codex 기본 원칙

- Repository를 열면 먼저 Root 및 가장 가까운 AGENTS.md를 읽는다.

- Build 성공만으로 기능 완료를 판단하지 않는다.
- UI는 실제 Browser에서 Pointer와 Keyboard로 확인한다.

- Placeholder, TODO, Mock, No-op Handler를 완료로 간주하지 않는다.

32. Local Windows Deployment 상세 명세
======================================================================

32.1 Production Process

- WebEditor Server: `127.0.0.1:3210`
- Metadata DB, Active Project Storage, Trash Storage, Backup은 로컬 고정 경로
- WebEditor Server는 승인된 Windows Service Wrapper 또는 Native Service로 실행
- `cloudflared`는 Windows Service로 실행
- 외부에 WebEditor Port를 직접 개방하지 않는다.

32.2 권장 외부 연결

Browser
→ `https://webeditor.dove9999.com`
→ Cloudflare Edge
→ Outbound-only Cloudflare Tunnel
→ `http://127.0.0.1:3210`
→ WebEditor

목표:

- 공인 IP 또는 Router Port Forwarding 없이 운영
- Local Origin IP와 Port를 외부에 직접 노출하지 않음
- HTTPS 제공
- Windows 시작 시 자동 실행
- Tunnel 장애와 App 장애를 구분할 수 있는 Health Monitoring

32.3 Local Storage Layout

예시:

C:\ProgramData\Dove9999\WebEditor\
├─ config\
│  ├─ app.json
│  └─ secrets\                 # ACL로 제한, Git 제외
├─ metadata\
│  └─ webeditor.db
├─ projects\
│  ├─ active\
│  │  └─ <projectId>\
│  │     ├─ runtime\
│  │     ├─ assets\
│  │     ├─ exports\
│  │     └─ manifests\
│  └─ trash\
│     └─ <projectId>\
│        ├─ runtime\
│        ├─ assets\
│        └─ trash-manifest.json
├─ backups\
├─ reports\
├─ logs\
└─ temp\

Project를 휴지통으로 보낼 때 Metadata 상태 변경과 Storage 이동을 하나의 Lifecycle Operation으로 관리한다. File System Rename이 원자적이지 않거나 다른 Volume을 건너는 경우 Copy → Checksum → Metadata Commit → Source Cleanup 순서와 보상 처리를 사용한다.

32.4 Health Endpoint

GET /health
- Process Liveness

GET /ready
- Metadata DB 연결
- Active/Trash/Backup Directory Write 권한
- Migration 상태
- Runtime Storage Integrity
- Theme Manifest 유효성
- Lifecycle Recovery 필요 여부
- 필수 Service Dependency

GET /health/tunnel
- 선택적으로 Tunnel 상태를 별도 수집
- 일반 사용자에게 내부 정보 과다 노출 금지

32.5 Service 시작 순서

1. Config와 Secret ACL 확인
2. Storage Directory 확인
3. 미완료 Lifecycle Operation 복구
4. Metadata Migration
5. Metadata DB Integrity Check
6. Active/Trash Manifest Integrity Check
7. Runtime DB Integrity Check
8. Theme Manifest 검증
9. Backup Policy 확인
10. App Server 시작
11. Ready 상태
12. cloudflared 연결
13. 외부 Synthetic Health Check

서비스 종료 시 새 Write를 차단하고 진행 중 Transaction을 종료한 뒤 DB를 Flush한다.

32.6 Backup

- Metadata DB Daily
- Active Project Runtime/Asset Daily Incremental
- Publish 직전 자동 Backup
- Schema Migration 직전 자동 Backup
- Permanent Purge 직전 선택적 Tombstone Backup 또는 정책에 따른 최종 Snapshot
- 최근 N개와 월간 Snapshot 유지
- Backup Manifest/Checksum
- Encryption at Rest 정책
- 월 1회 Restore Drill
- Restore 결과를 자동 Report

Trash는 Backup이 아니다. 사용자가 Project를 휴지통으로 옮긴 상태와 별개로 Backup 정책을 운영한다.

32.7 Recycle Bin Retention

기본 정책은 설정 가능하게 한다.

- 자동 영구 삭제 없음 또는 명시적 보존 기간
- 보존 기간을 활성화할 경우 사전 고지
- 만료 예정 Project 표시
- Production에서는 자동 Purge 전에 별도 승인 정책 가능
- Purge 후 Tombstone/Audit Metadata는 보안·감사 정책 범위에서 유지

32.8 Domain과 HTTPS 검증

- `webeditor.dove9999.com` DNS Route
- 유효한 HTTPS Certificate
- HTTP → HTTPS
- WebSocket/SSE 사용 시 Tunnel 통과
- Large Upload 제한
- Cache Header
- Security Header
- 실제 외부 Network에서 Login/Editor/Runtime 확인
- Origin 직접 접근 차단

32.9 Windows 재부팅 검증

1. 정상 Shutdown 후 재부팅
2. App Service 자동 시작
3. cloudflared 자동 시작
4. `/ready` PASS
5. Domain HTTPS 접근
6. Active Project 열기
7. Trash Project 목록 확인
8. Published Runtime 데이터 조회
9. Runtime Browser Theme Preference 유지
10. Audit/Log 이상 여부 확인

32.10 장애 복구 Drill

- App Process 강제 종료
- Windows 재부팅
- Tunnel 중단
- Disk Full Simulation
- Metadata DB Backup Restore
- Runtime DB Restore
- Trash 이동 중 강제 종료
- Restore 중 강제 종료
- Purge 중 강제 종료

각 Drill에서 Partial State, Orphan File, Double Restore, Cross-project Data Leak이 없어야 한다.

RISK-01 기능 범위 폭증

대응: Token Hash, Perceptual Color Distance, Contrast, Screenshot Similarity를 자동 검사한다.

대응: 공식 Palette와 License를 조사하고 참고 계열·변형 규칙·License Note를 Manifest에 기록한다. 브랜드 이름을 제품 Theme 이름으로 그대로 쓰지 않고 적응형 이름을 사용한다.

RISK-08 편집 Theme와 Runtime Theme 불일치
대응: Theme Revision을 Published Snapshot에 포함하고 Runtime Resolve 우선순위와 Cache Invalidation Test를 둔다.

RISK-09 Browser별 Theme Preference 오염
대응: Storage Key에 Runtime App ID, Project ID, Theme Schema Version을 포함하고 Value를 Allowlist로 검증한다.

RISK-10 Binding Edge가 그림으로만 존재
대응: Edge 생성과 Binding Record 생성은 동일 Transaction/Command로 처리하고 Query Preview와 실행 E2E를 필수화한다.

RISK-11 Node 연결 방향이 모호함
대응: Input은 좌측, Output은 우측으로 고정하고 Arrow, Label, Connection Preview, Invalid Feedback을 동시에 제공한다.

RISK-12 직교 Routing이 복잡한 Graph에서 실패
대응: ELK Port Side Constraint, Obstacle Avoidance, Bend Penalty, Max Bend Rule, Manual Waypoint Fallback, Visual Regression.

RISK-13 Mock Data로 완료 처리
대응: E2E가 실제 Test DB Insert/Select/CRUD와 DB Assertion을 확인해야 Gate를 통과한다.

RISK-14 Soft Delete 중 일부 데이터만 이동
대응: Lifecycle Operation Journal, Manifest/Checksum, Transaction 또는 Compensation, Startup Recovery.

RISK-15 Restore 이름 충돌 및 ID 충돌
대응: Stable Project ID 유지, Display Name Conflict Resolver, Route/Slug 재검증, Preview 후 Restore.

RISK-16 Permanent Purge 오삭제
대응: Recycle Bin에서만 허용, Project Name 재입력, 영향도 표시, 별도 권한, Optional Final Backup, Dry Run, Audit.

RISK-17 Trash를 Backup으로 오인
대응: Trash와 Backup을 구조·UI·Policy에서 명확히 분리하고 Restore Drill을 별도로 수행한다.

RISK-18 100개 Project 검증이 형식적 복제로 끝남
대응: Corpus Category와 Coverage Constraint, Unique Sentinel, Project Fingerprint Diversity, Manifest Validator를 사용한다.

RISK-19 Project 간 데이터 누출
대응: Project ID Scope를 API/DB/File Path에 강제하고 100개 Corpus에서 Cross-project Sentinel Search를 수행한다.

RISK-20 전수 검증 누락
대응: Registry 기반 Feature Inventory, Requirement Matrix, Uncovered Item Gate, SKIP/TODO 금지.

RISK-21 Visual Test Baseline 남용
대응: Baseline 변경 시 Diff, 사유, Reviewer 승인, Requirement Reference를 요구한다.

RISK-22 외부 공개 보안
대응: Localhost Bind, Tunnel, Auth, CSRF, Rate Limit, Safe Upload, Arbitrary SQL/JS 금지, Security Header.

RISK-23 Codex 장시간 작업 중 요구사항 이탈
대응: AGENTS.md, Repository Skill, REQ ID, Phase Status, Inventory, Reviewer Agent, Evidence Gate.

RISK-24 Library/API 변경
대응: Lockfile, ADR, 공식 문서 확인, Upgrade PR, 무단 Major Upgrade 금지.

RISK-25 Windows Service 시작 순서 문제
대응: Ready Probe, Retry/Backoff, Dependency-independent Tunnel, Startup Recovery, Reboot E2E.

RISK-26 Disk 부족과 Backup 증가
대응: Disk Budget, Retention, Alert, Temp Cleanup, Purge 전 여유 공간 검사.

RISK-27 사용자 테마와 접근성 충돌
대응: Editor가 Custom Theme를 저장할 때 Contrast Gate를 실행하고 실패 항목을 명확히 표시한다. 운영 배포 가능한 Theme는 필수 Gate를 통과해야 한다.

RISK-28 Lucide 전체 Icon 검색 성능
대응: Icon Metadata Index와 Virtualized Grid를 사용하며, 모든 Icon Component를 초기 Bundle에 정적으로 포함하지 않는다.

# WebEditor working agreements

## Mission

Build the statistical visual web-service builder defined in:
- `docs/00-source-requirements.md`
- `docs/00a-added-requirements.md`
- `docs/01-product-spec.md`

Preserve source intent. Do not silently reduce, substitute, or omit requirements.

## Read before editing

1. `docs/00-source-requirements.md`
2. `docs/00a-added-requirements.md`
3. `docs/implementation-status.md`
4. `docs/requirement-traceability.json`
5. The closest nested `AGENTS.md`
6. Relevant ADR and feature specification

## Architecture invariants

- Editor and Runtime Renderer are separate.
- Metadata DB, test runtime DB, and production runtime DB are separate.
- Draft and Published versions are separate.
- Published runtime uses a left-side page navigation.
- Page icons are stored as validated Lucide icon names.
- Bindings use stable IDs, never display names.
- Input ports are on the left; output ports are on the right.
- Graph edges are direction-aware and predominantly orthogonal with small rounded bends.
- Runtime API never accepts arbitrary SQL or JavaScript.
- Table and field physical identifiers are immutable internal names.
- UI primitives come from shadcn/ui; general icons come from Lucide.
- Page/palette DnD and canvas layout responsibilities must not be mixed without an ADR.
- Drop preview and final drop must use the same placement-candidate calculation.
- Project delete is soft delete. Permanent purge is only available from the recycle bin.
- Trash is not a backup.
- Editor theme revisions and runtime user theme preferences have separate ownership.
- Runtime theme preference is namespaced by app/project/schema and validated against an allowlist.
- Feature registries and the test inventory must remain synchronized.

## Delivery method

- Work phase by phase and vertical slice first.
- Update `docs/implementation-status.md` before and after substantial work.
- Do not mark a phase complete while required tests fail.
- Do not leave placeholders, fake handlers, mock persistence, TODO-only implementations, or no-op commands for source requirements.
- Preserve existing working behavior unless the specification explicitly requires a change.
- Add or update inventory entries and generated test matrices whenever a Page type, Layout preset, Element, Binding type, Theme, lifecycle state, or API is added.
- Do not report the whole product complete until exhaustive verification and the 100-project operational corpus both pass.

## Validation

Run the subset relevant to the phase and the full release gate before final completion:

- `pnpm format:check`
- `pnpm lint`
- `pnpm typecheck`
- `pnpm test`
- `pnpm test:integration`
- `pnpm test:component`
- `pnpm test:e2e`
- `pnpm test:visual`
- `pnpm test:inventory`
- `pnpm test:themes`
- `pnpm test:exhaustive`
- `pnpm test:corpus:verify`
- `pnpm test:deployment`
- `pnpm build`
- `pnpm verify:release`

Inspect the actual application in a browser for interaction-heavy changes. Check browser console, network failures, keyboard operation, focus visibility, persisted state, and reload/restart behavior.

## Evidence

Do not claim PASS without:
- command result
- test or inventory reference
- requirement IDs
- build/commit ID
- browser trace or screenshot when visual/interactive
- DB/file assertion when data is affected

## Data safety

- Never delete or rewrite production runtime data without a migration plan, backup, impact report, and explicit destructive action.
- Tests must use isolated test workspaces and real test databases.
- Project soft delete must preserve metadata, runtime DB, assets, bindings, and theme state.
- Restore and purge must use lifecycle journals, manifests, checksums, and recovery logic.
- Permanent purge requires a dry run and stronger confirmation.
- Never put secrets, tunnel tokens, credentials, or user data in Git.

## Theme safety

- Use semantic tokens.
- Keep the 60-theme manifest and generated code synchronized.
- Validate required contrast and token completeness.
- Record reference family and license/adaptation notes.
- Do not clone external brand themes blindly.
- Runtime user preferences must not mutate the project default.

- Use current official documentation.

- Do not upgrade a major dependency while implementing an unrelated feature.

- browser evidence
- requirement IDs

# Interaction rules

- Page reorder and palette drag must have a real drag overlay and keyboard support.
- Element placement must show the actual grid-snapped candidate rectangle before drop.
- The preview candidate and committed placement must match.
- Page icon changes must use a searchable Lucide picker and persist to runtime.
- Runtime page navigation stays on the left.
- Graph input handles stay on the left; output handles stay on the right.
- Edges are directional, mostly straight/orthogonal, and use small rounded corners at bends.
- Node moves must trigger route recalculation without losing the binding.

# Project lifecycle rules

- The normal delete button performs soft delete only.
- Soft-deleted projects leave the active list and enter the recycle bin.
- Restore preserves project ID and all project-owned data.
- Name/route conflicts must be resolved explicitly.
- Permanent purge is available only from the recycle bin and requires impact preview and stronger confirmation.
- Use operation journals, manifests, checksums, transactions or compensation, and startup recovery.
- Trash is never described as a backup.

# Theme rules

- Use the 60-theme manifest as a generated source of truth.
- Use semantic tokens rather than scattered hard-coded colors.
- Validate token completeness, contrast, uniqueness, and visual regression.
- Editor changes create/publish a theme revision that runtime can apply.
- Runtime users may override the allowed theme in their browser.
- Browser preference must be namespaced and allowlist-validated.
- A missing or removed preference falls back to the project default.

# Required evidence

Do not say complete without:
- changed file list,
- relevant test names and command results,
- browser verification for UI,
- DB/file assertions for data changes,
- requirement IDs covered,
- inventory coverage,
- report and trace paths.

- exhaustive inventory-driven verification must pass,
- all 60 themes must pass,
- exactly 100 diverse real test projects must be generated,
- all 100 projects must pass create/edit/save/reload/restart/runtime/data/navigation/theme/trash/restore scenarios,
- cross-project leak and orphan counts must be zero,
- no required test may be skipped or expected to fail.

# Prohibitions

- No fake DB arrays in place of runtime DB requirements.
- No edge-only visual bindings without executable binding records.
- No arbitrary SQL or user JavaScript.
- No silent destructive schema changes.
- No hard delete from the normal project list.
- No non-Lucide general UI icons.
- No replacement of shadcn primitives with another general UI kit.
- No theme catalog made from near-identical token sets.
- No completion claim based on a small sample instead of the full inventory and corpus.
- No baseline update solely to hide a visual regression.

41.2 충돌 및 해석 결과

- 원문의 Page 우측 빨간 휴지통은 Page 삭제 기능이다. 추가 요구사항의 Project 삭제 버튼과 별개로 유지한다.
- Project 일반 삭제는 Soft Delete이지만 Page 삭제는 기존 영향도 확인 및 Undo/Version 정책을 따른다. Page 단위 별도 Recycle Bin은 현재 요구사항에 포함되지 않는다.
- Editor Theme 변경의 “운영 화면 자동 적용”은 Draft 변경이 무검증으로 Production에 노출된다는 의미가 아니다. Theme Validation을 통과한 Published Theme Revision이 Runtime에 자동 활성화되는 안전한 흐름으로 구현한다.
- Runtime 사용자의 Browser Theme는 Project Default를 변경하지 않는 개인 Override다.
- “100여개”는 자동화와 합격 판정의 명확성을 위해 100개로 고정했다.
- 유명 Theme는 그대로 복제하지 않고 공식 자료를 참고하여 Semantic Token으로 재구성하며 License와 Attribution을 별도로 검토한다.
- Node의 좌우 연결점은 시각적 위치뿐 아니라 Connection Semantics를 의미한다. 좌측은 Input/Target, 우측은 Output/Source다.
- “최대한 직선”은 완전한 단일 직선만 허용한다는 뜻이 아니라, 장애물을 피해 수평·수직 Segment로 구성하고 Bend만 작은 Radius로 처리한다는 의미로 확정한다.

41.3 추가 요구사항 완료 판정

ADD-001부터 ADD-010은 각각 Requirement ID, 구현 Phase, Test ID, Evidence Artifact에 연결되어야 한다. 어느 하나라도 `OPERATIONALLY VERIFIED` 수준에 필요한 검증이 완료되지 않으면 추가 요구사항 반영은 완료가 아니다.

42.1 Lifecycle State

Project 상태:

ACTIVE
TRASHING
TRASHED
RESTORING
PURGING
PURGE_FAILED
PURGED

정상 State Transition:

ACTIVE
  → TRASHING
  → TRASHED
  → RESTORING
  → ACTIVE

TRASHED
  → PURGING
  → PURGED

실패 Transition:

TRASHING 실패
  → Operation Journal을 기준으로 ACTIVE 또는 TRASHED 중 일관된 상태로 복구

RESTORING 실패
  → TRASHED로 되돌리거나 Resume 가능한 상태 유지

PURGING 실패
  → PURGE_FAILED
  → Retry 또는 Manual Recovery

42.5 Restore

Endpoint 예:

POST /api/trash/:projectId/restore

Request:
{
  "expectedTrashRevision": 3,
  "nameConflictStrategy": "prompt",
  "slugConflictStrategy": "prompt"
}

충돌 정책:

- Display Name만 충돌: 동일 이름 허용 또는 사용자 Rename 선택
- Slug 충돌: 자동 덮어쓰기 금지
- Project ID 충돌: 이미 ACTIVE인 동일 ID가 있으면 심각한 무결성 오류로 차단
- Storage Path 충돌: 자동 덮어쓰기 금지
- Theme가 더 이상 허용되지 않음: Project Default Fallback을 Preview에 표시
- Schema Version이 구버전: Restore 후 별도 Migration Plan 적용

Restore 완료 후 검증:

- Project ID 동일
- Page/Element/Binding ID 동일
- Runtime Row Sentinel 동일
- Asset Checksum 동일
- Published Snapshot 동일
- Theme Revision 동일 또는 명시된 Migration 결과
- Active 목록과 검색에 표시
- Runtime Route 정상
- Audit Log 기록

42.6 Permanent Purge

Endpoint 예:

POST /api/trash/:projectId/purge/preview
POST /api/trash/:projectId/purge

Preview는 다음을 반환한다.

- 제거될 Metadata Record 수
- Runtime DB 파일
- Asset 파일
- Export/Backup Reference
- Search Index
- Published Snapshot
- 예상 회수 용량
- 현재 Backup 존재 여부
- 차단 조건

Purge Confirmation:

- Recycle Bin에서만 가능
- Project 이름 또는 지정 Phrase 직접 입력
- 관리자 권한 또는 별도 Permission
- Preview ID와 짧은 Expiration
- Revision 재검증
- 선택적 Final Snapshot
- 실행 중 Editor/Runtime 접근 차단

Purge 이후:

- Project Data/Asset의 Orphan Scan
- Search/Cache 정리
- Audit Tombstone 유지
- Operation Result와 Checksum Report
- Backup 정책상 남은 복사본이 있으면 UI에 명확히 표시

42.7 장애 주입 Test

다음 지점에서 Process를 강제 종료한 뒤 재시작한다.

- TRASHING Metadata Commit 전
- File Move 중간
- Checksum 후 Final Commit 전
- RESTORING File Move 중간
- Restore Metadata Commit 전
- PURGING DB 삭제 후 Asset 삭제 전
- Audit Event 기록 전

각 경우 Startup Recovery는 Operation Journal을 읽고 Resume 또는 Compensation한다. 사용자에게 보이는 최종 상태는 ACTIVE, TRASHED, PURGED 중 하나로 일관되어야 하며, 동일 Project가 Active와 Trash에 동시에 나타나면 안 된다.
